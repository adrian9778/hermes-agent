## 一、本模块目标

补齐调度器与定时任务：

- `cron/` 目录（**顶层 57 个 py + `cron/scripts/` 下 2 个 = 59 个 py 文件**）；
- 触发抽象与调度器主循环（含多 profile 复用与外部 provider）；
- 任务定义与任务存储（`jobs.py` 门面 + `jobs_*.py` 一族）；
- 执行记录（executions 账本 + occurrences 槽位）；
- 跨平台投递与重启安全投递队列；
- 失败、重试、事故与诊断；
- **Kanban 多代理工作队列的调度器**（`hermes_cli/kanban.py` + `gateway/kanban_watchers*.py`）。

### 2.1 谁在跑 ticker

- **网关侧**：`gateway/run_bootstrap.py` · `_start_gateway_start_cron_and_housekeeping` `+0`
  → `cron/scheduler_provider.py` · `resolve_cron_scheduler` `+0` /
  `scheduler_for_profile_mode` `+0` → 用 `cron/scheduler_thread.py` ·
  `SupervisedTickerThread` `+0` 起一个受监督守护线程跑 `provider.start`。
  一个 gateway 进程为 **所有** profile 的 store tick（`gateway.multiplex_profiles` 门控的是
  adapter，不是 cron）；`gateway/run.py` · `_cron_tick_profile_homes` `+0` 返回要 tick 的 home 列表，
  `gateway/run.py` · `_cron_profile_gate` `+0` 判断"该 profile 由自己的 gateway tick，宿主站下"。
- **网关内还有一条 misfire 兜底**：`gateway/run.py` · `_housekeeping_misfire_catch_up` `+0`
  每 5 个 housekeeping 周期调 `cron/scheduler_provider.py` · `fire_overdue_jobs` `+0`
  （只对**非** `InProcessCronScheduler` 的外部 provider 有意义：built-in 的 tick loop 自愈，
  对 built-in 直接返回 0）。
- **独立进程**：`python -m cron.scheduler`（`cron/scheduler.py` 文件末尾的
  `if __name__ == "__main__"` 分支；`--external-worker-file` 走重启安全外部 worker 协议，
  `finish_worker_boot` `+0` 先执行，由 `cron/worker_bootstrap.py` 接管）。
- **手动**：`hermes_cli/cron.py` · `cron_tick` `+0`（headless，`tick(headless=True)`）。
- `gateway/run.py` · `_start_cron_ticker` `+0` **是 DEPRECATED shim**，只跑内置 in-process 循环，
  真实触发已由 `CronScheduler` provider 承担。

## 四、任务生命周期

调度层与账本层有**两套**状态机，不要混为一谈。

### 4.1 调度层（`cron/jobs.py`）

```mermaid
stateDiagram-v2
    [*] --> Scheduled: create_job（enabled=true, next_run_at 已算）
    Scheduled --> Claimed: claim_dispatch（火化 claim）
    Claimed --> Running: try_register_running_job（per-(home,job_id)）
    Running --> Scheduled: mark_job_run + advance_next_runs（recurring，推进 next_run_at）
    Running --> Completed: mark_job_run（one-shot 终态，terminal）
    Running --> Error: 失败（state=error, last_error 写入）
    Error --> Scheduled: _is_recoverable_error_job（recurring 可恢复）
    Scheduled --> Paused: pause_job（带 paused_reason）
    Paused --> Scheduled: resume_job
    Scheduled --> [*]: remove_job / one-shot 完成
    Paused --> [*]: remove_job
```

关键不变量（`cron/AGENTS.md` 明确要求不得削弱）：

- **`tick()` 在派发之前**推进 `next_run_at`，并在同一次保存里写下 `pending_slot`
  —— 跨"跑一半崩掉"是 at-most-once；
- 扫描发现 `pending_slot` 但 owner 已死时，`cron/occurrences.py` · `unclaimed_pending_slot` `+0`
  会**恰好一次**恢复该时刻；executions 账本的 `scheduled_instant` 阻止第二次开火；
  `cron.catch_up_missed: false` 会跳过超出 grace 的错过并记原因。**绝不静默丢槽位**；
- 补跑窗口 = 周期的一半，夹在 120s–2h（`cron/jobs.py` · `_compute_grace_seconds` `+0`）；
  一次性任务给 120s grace（`ONESHOT_GRACE_SECONDS = 120`）；
- 每个 home 一个 tick 锁（`<HERMES_HOME>/cron/.tick.lock`），跨进程只允许一个 tick；
- **Headless tick 拒发，不 spawn**：`hermes cron tick` 走 `tick(headless=True)`，
  `cron/scheduler_gateway_gate.py` · `refuse_agent_jobs_without_gateway` `+0` 在发现
  "无 gateway 拥有该 home"时跳过 agent job（`last_fire_error` 戳，每 tick 一次警告，
  due instant 不动），而不是让 `run_canonical_job → connect_gateway → ensure_gateway_runtime`
  spawn 一个不受管的 daemon；
- **`cron/lifecycle_guard.py` · `check_gateway_lifecycle` `+0`** 在 `create_job` `+0` 的 `+73`
  被调，拒绝会在网关内部重启/停掉网关的命令（SIGTERM 重生循环）；
- **Inactivity watchdog**：`cron/scheduler.py` · `_cron_inactivity_seconds` `+0`（默认 600s 空闲，
  `HERMES_CRON_TIMEOUT` 覆盖，0 = 不限）。它是**空闲时间**而非墙钟——卡住的会话会被硬中断
  （不能独占调度器），而长而活跃的任务不会被砍。附带的脚本由独立的脚本超时
  （`_DEFAULT_SCRIPT_TIMEOUT` = 3600s）约束。

### 4.2 账本层（`cron/executions.py` + `cron/incidents.py`）

- **executions**：每次尝试一行，终态 `completed` / `failed` / `unknown` / `cancelled` / `missed`
  （**5 个**，旧文档写 3 个；`_TERMINAL_STATES` `+0` 在 `cron/executions.py`）且**不可变**；
  "unknown" 只在 owner 进程被证明已死之后才写（启动时间读数与 claim 时的指纹不符**不算**死亡证明）；
  `FIRER_FINISHED_STATES = frozenset({"completed","failed","cancelled"})` —— 这三态由"开火方"
  记账，receipt recovery / external-worker waiter / dead-owner sweep 都视为**终态**，
  永不重放或重记；
- **incidents**：`INCIDENT_STATES = ("detected","alerted","resolved","closed")`。
  只有 `closed`（操作者 ack）是终态；`resolved` 的错误再次出现会重新开成 `detected`；
  错误文本变化会铸出新的 incident id。两者共用同一个 `cron/executions.db`。

```mermaid
    participant DQ as cron.delivery_queue

    TK->>TK: retirement.work() 门控 / _acquire_tick_lock_or_degrade
    TK->>TK: estop check / can_dispatch gate / _pre_dispatch_housekeeping
    TK->>JB: get_due_jobs()
    TK->>JB: _advance_or_drop_recurring（先推进 next_run_at，at-most-once）
    TK->>OC: pending_slot_stamp / unclaimed_pending_slot（死 owner 恰好一次恢复）
    TK->>EX: create_execution(scheduled_instant=...)
    TK->>RJ: _submit_with_guard → _process_due_job → run_one_job
    RJ->>EX: 若无 execution_id，建 execution（source="direct"）
    RJ->>RJ: _launch_external_cron_worker（重启安全 worker）
    RJ->>RJ: run_job（非 no_agent 任务转 run_canonical_job）
    AUTH->>AUTH: journal / pause / reconcile
    AUTH->>AG: run_conversation（cron 会话 skip_memory=True）
    AG-->>AUTH: 结果
    AUTH-->>RJ: (success, full_output_doc, final_response, error)
    RJ->>DL: _deliver_result（origin / home / explicit / bot-chat / room）
    DL->>DL: _resolve_delivery_targets（无适配器时入 delivery_queue）
    DL->>DQ: enqueue_and_wait（重启安全 worker 路径）
    DQ-->>DL: 终态（delivered / suppressed / unknown）
    RJ->>JB: mark_job_run（写输出、推进/终结、更新 incident）
```

### 5.2 投递的三个车道

- **本地 live adapter**：网关进程内直接用适配器发送（E2EE / relay 需要，所以 loop 被传进 ticker）；
  `cron/scheduler_delivery.py` · `_deliver_via_live_adapter` `+0` 先试 live 路径，
  `_live_send_text` `+0` / `_live_send_media` `+0` 走 adapter 的 `send_text` / `send_media`；
- **重启安全交接队列**（`cron/delivery_queue.py`）：脱离网关 cgroup 的 worker 无法持有
  relay/E2EE 适配器对象，于是把最终发送排进队列，由网关**至多认领一次**
  （`claim_next` `+0` 原子 CAS，`status: pending → delivering → delivered/failed/unknown/suppressed`）；
  认领后网关死掉则该行标为 unknown 且**永不重试**（丢一次比重复发一次更安全）；
  `recover_abandoned` `+0` 把死 owner 的行 fence 成 unknown，**不重放**，
  并把 outcome 回写（job `delivery_failed` + error、ledger `failed`）；
- **进程外 standalone sender**：平台插件可在 `PlatformEntry.standalone_sender_fn` 里提供
  无共驻网关时的发送实现（配 `cron_deliver_env_var` 才能端到端可用）；
  `cron/scheduler_delivery_standalone.py` · `_standalone_send` `+0` 实现 HTTP 直发，
  `_queue_for_live_reconnect` `+0` 处理 relay 重连场景。

### 5.3 其它要点

- 定时任务触发的是**独立的 cron 会话**，`skip_memory=True`（记忆 provider 在 cron 中刻意不跑）；
- 可续投递可以把简报镜像/播种到面向回复的会话（origin、无 origin 的 home 兜底、
  用户手写的裸平台 home、显式 opt-in 目标）；`all` 展开不获得 home 镜像资格
  （`cron/scheduler_delivery.py` · `_maybe_mirror_cron_delivery` `+0` / `_seed_cron_session` `+0`）；
- `[SILENT]` 类响应会抑制投递（`cron/scheduler.py` · `_is_cron_silence_response` `+0`）；
- 会话内的空闲看门狗是**空闲时间**而非墙钟：卡住的会话会被硬中断，长而活跃的任务不会被砍；
  预跑脚本由独立的脚本超时约束（`cron/scheduler_script.py` · `_get_script_timeout` `+0`，
  默认 3600s）；
- **重启安全外部 worker**：`cron/scheduler.py` · `_launch_external_cron_worker` `+0` 起一个
  `-m cron.scheduler` 子进程（`--external-worker-file` + `--ack-file`），worker 先跑
  `cron/worker_bootstrap.py` · `worker_bootstrap` `+0` 激活 PM 依赖，再 `finish_worker_boot` `+0`，
  最后读 payload 执行。父进程 `_wait_for_external_cron_worker` `+0` 等 worker 终态。
  这是"gateway 重启后 cron 任务仍能交付"的关键路径。

## 六、失败与重试

- **失败记录**：executions 账本记每一次尝试（5 终态）；incidents 把同类失败归并成事故并做
  ack 去重，避免同一任务同一错误每次开火都 ping 操作者（`cron/incidents.py` ·
  `upsert_incident` `+0`，按 `(job_id, error signature)` 归并）；
- **重试策略**：
  - `cron/unreachable_retry.py` —— "根本没到达模型"（如刚唤醒、VPN 未就绪）的有界自动重跑
    （`plan_retry` `+0` / `will_retry` `+0`）；
  - `cron/quota_hold.py` —— provider 明确给出 `retry after <N>s` 且整条 fallback 链都不可用时，
    按窗口挂起该任务的开火（`plan_hold` `+0`），而不是按节奏重复必然失败；
  - 一次性任务的 running claim 有 TTL（`HERMES_CRON_TIMEOUT`），owner 已死才可被回收；
  - `cron/extra_fire.py` —— off-tick fire（webhook / misfire）的槽位记账
    （`pending_slot` `+0` / `settle` `+0`），确保 extra fire 不偷走 tick 的槽位；
- **超时控制**：`cron/scheduler.py` · `_cron_inactivity_seconds` `+0`（默认 600s 空闲，
  `HERMES_CRON_TIMEOUT` 覆盖，0 = 不限）约束 agent 会话；
  预跑脚本另受 `cron/scheduler.py` · `Const:_DEFAULT_SCRIPT_TIMEOUT`（3600s）约束，
  读取路径是 `cron/scheduler_script.py` · `_get_script_timeout` `+0`；
- **降级处理**：`cron/scheduler_failure_copy.py` 把分类后的失败翻成"发生了什么 + 该怎么办"的
  一句话通知，并给出确切的 `hermes cron` 命令与真实输出目录
  （`classify_cron_failure_reason` `+0` → `provider_failure_notice` `+0` /
  `generic_failure_notice` `+0` / `script_timeout_notice` `+0` / `inactivity_notice` `+0`）；
- **诊断**：`cron/scheduler_diagnostics.py` 生成私有 run-document 诊断（与投递摘要分离）；
  `cron/scheduler_thread.py` 的监督层负责"ticker 线程已经死了但没人发现"这类静默失效
  （`ticker_heartbeat` 冻结 → 复活）；
  `cron/scheduler.py` · `_maybe_reap_dead_owners` `+0` 按 300s 节流回收死 owner 的 claim；
  `cron/store_health.py` · `note_unwritable` `+0` / `dispatch_blocked` `+0` 处理 store 不可写降级
  （read-only/full/denied 时 tick 降级但仍跑 MCP 孤儿清扫）；
- **misfire 兜底**：`cron/scheduler_provider.py` · `fire_overdue_jobs` `+0` 在 gateway
  housekeeping 每 5 周期跑一次，对**外部 provider**（非 `InProcessCronScheduler`）补发
  "外部 HTTP fire 从未到达"的 job（built-in 的 tick loop 自愈，对 built-in 直接返回 0）。

## 七、本模块结论

本模块补齐了调度器与定时任务的主干逻辑。五个必须记住的结构性事实：

1. **`cron/scheduler.py` 是门面**：`run_job` `+0` 与 `run_one_job` `+0` 留在门面；
   `tick` 在 `cron/scheduler_tick.py`，投递在 `cron/scheduler_delivery.py`，预检在
   `cron/scheduler_preflight.py`，prompt 在 `cron/scheduler_prompt.py`，脚本在
   `cron/scheduler_script.py`，canonical agent 路径在 `cron/scheduler_authority.py`。
   `cron/__init__.py` 在包入口再导出 `tick`（`from cron.scheduler import tick`）。

2. **"何时开火"被抽成 provider**（`cron/scheduler_provider.py` · `CronScheduler`），
   而"怎么执行 + 怎么投递"始终留在 `cron/scheduler.py` · `run_job` / `run_one_job` 与
   `cron/scheduler_delivery.py` · `_deliver_result`，provider 不得重实现它们。
   默认 provider 是 `InProcessCronScheduler`（60s ticker，支持 multiplex 多 profile 复用）；
   外部 provider（当前只有 `plugins/cron_providers/chronos/` 的 `ChronosCronScheduler`）
   通过 NAS webhook 触发，只服务单个 home。

3. **记录是三层**：任务存储（`cron/jobs.py` + `jobs_*.py` 8 个兄弟）、槽位身份
   （`cron/occurrences.py`）、执行账本（`cron/executions.py`，5 终态）+ 事故
   （`cron/incidents.py`）。executions 与 incidents 共用 `cron/executions.db`。

4. **投递是三个车道 + 一个 legacy 文件**：live adapter / 重启安全交接队列
   （`cron/delivery_queue.py`，SQLite CAS，至多认领一次）/ standalone sender
   （`cron/scheduler_delivery_standalone.py`）。`cron/bot_chat_legacy.py` 是**遗留**，
   不再是活投递路径（活路径在 `scheduler_delivery.py` · `_deliver_to_bot_chat` `+0`）。

5. **Kanban 是另一个调度器**：多代理工作队列，board 是硬隔离边界，dispatcher 默认跑在
   gateway 内（`gateway/kanban_watchers.py` · `_kanban_dispatcher_watcher` `+0`，60s 循环），
   worker 存活用 `(pid, started_at)` 启动时间指纹判定（防 PID 回收误杀）。

后续模块继续展开并发、错误、测试、部署和源码索引。
