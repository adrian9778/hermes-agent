## 一、本层目标

本层只做一件事：选一个**真实、最小、可跟读**的例子，把请求从用户输入一路追到最终响应，覆盖：

1. 前端/客户端入口；
2. CLI 参数解析与 Agent 装配；
3. 核心 Agent 循环；
4. LLM API 调用；
5. 工具调用分发（如果发生）；
6. 会话持久化；
7. 响应回到界面。

本层只走**主成功路径**。失败、重试、压缩、并发、插件钩子、缓存失效等细节先点到为止，不展开。

## 二、选择的最小例子

例子命令：

```bash
hermes -z "hello"
```

含义：以非交互方式启动 Hermes CLI，发送一条用户消息 `hello`，等待 Agent 完成并返回最终文本。

选择它的原因：

- 入口最短，不涉及 TUI、Electron、消息网关；
- 仍然经过真实 `AIAgent` 与真实对话循环 `agent/conversation_loop.py` · `run_conversation` `+0`；
- 能覆盖"用户输入 → CLI → Agent → LLM → 响应 → 落库"的完整主路径；
- 如果模型决定调用工具，还能自然展示 `model_tools.py` · `handle_function_call` `+0` 与
  `tools/registry.py` 的调用关系。

`-z` / `--oneshot` 参数定义在 `hermes_cli/_parser.py` · `add("-z", "--oneshot", ...)` `+0`（该文件
第 133 行的 `add` 调用；同文件第 23 行的 `_KNOWN_FLAGS` 集合也登记了它）。

## 三、脱敏输入/输出

### 3.1 输入

```text
argv = ["hermes", "-z", "hello"]
user_message = "hello"
```

### 3.2 输出（示意，实际文本由模型决定）

```text
Hello! I'm Hermes, your personal AI agent. What would you like to work on?
```

### 3.3 关键副作用

- 在 `~/.hermes/state.db` 的 `sessions` / `messages` 表中新增或更新会话记录；
- 在 `~/.hermes/logs/agent.log` 中写入 INFO 级运行日志；
- 如果发生工具调用，工具结果会作为 `tool` 消息追加到本轮消息列表。

> `HERMES_HOME` 决定上述路径。默认 profile 是 `~/.hermes`；`-p <name>` 会把它切到另一个
> profile 目录（见 [07-配置体系与环境变量](./07-配置体系与环境变量.md)）。

## 五、逐跳走读（只走主路径）

### 5.1 入口：`hermes_cli/main.py` · `main` `+0`

- 文件：`hermes_cli/main.py`（3637 行）
- 函数：`main` `+0`
- 作用：CLI 进程入口，做启动准备，然后构建 parser 并分发到子命令。

关键动作（按源码顺序）：

2. `_warn_if_unsupervised_pid1` `+0`：当本进程是 PID 1 且上方无 reaper 时告警；
3. Windows 下配置 UTF-8 stdio；
4. `_apply_profile_override` `+0`：**在导入重量级模块之前**预解析 `--profile` / `-p` 并设置
   `HERMES_HOME`——这是 profile 隔离能生效的前提；
5. 启动自愈：清理旧更新残留、扫描过期 bytecode、自愈半成品 venv；
6. Termux 相关分支：`_is_termux_startup_environment` `+0`、`_sync_bundled_skills_for_startup` `+0`；
7. `_config_default_interface_early` `+0` / `_wants_tui_early` `+0`：在 argparse 之前就决定是否走 TUI；
8. 调用 `build_top_level_parser()` 构建 parser；
9. 最终调用 `args.func(args)`，进入 `cmd_chat(args)`。

### 5.2 参数解析：`hermes_cli/_parser.py` · `build_top_level_parser` `+0`

真实符号：

- 文件：`hermes_cli/_parser.py`
- 函数：`build_top_level_parser` `+0`
- 作用：构建顶层 parser、subparsers 和 chat subparser。

对 `hermes -z "hello"` 来说，`-z` 是 chat 子命令的"一次性消息"参数（`metavar="PROMPT"`），
最终 `args.func` 被设置为 `cmd_chat`。

### 5.3 子命令入口：`hermes_cli/main.py` · `cmd_chat` `+0`

真实符号：

- 文件：`hermes_cli/main.py`
- 函数：`cmd_chat` `+0`
- 作用：解析 `--in` / `--resume` / `--continue`、安全模式、TUI 选择，然后进入 CLI 或 TUI 运行路径。

主路径（按源码顺序，比上一版文档多了 bootstrap 与 provider 守卫两段）：

1. `_apply_safe_mode(args)` `+0`：应用安全模式；
2. `_apply_user_config_bypass(args)` `+0` / `_guard_noninteractive_user_config(args)` `+0`：用户配置旁路与
   非交互场景守卫；
3. `stream_json_requested(args)` `+0`（来自 `hermes_cli/stream_json.py`）：结构化 stdout 是非交互协议，
   它会**覆盖** `HERMES_TUI` / `display.interface`；否则才调用
   `_resolve_use_tui(args)` `+0`（定义在 `hermes_cli/main_tui_launch.py`，**已不在 main.py 内**）；
4. `_resolve_chat_session_args(args, use_tui)` `+0`：归一化 `--in` / `--resume` / `--continue`；
5. `_warn_retired_xai_models()` `+0`：已退役模型告警；

7. `_has_any_provider_configured()` `+0`：没有任何可用 provider 时走 `_first_run_setup_guard(args)` `+0`

8. `_start_chat_background_prefetch()` `+0`：启动后台预取（工具发现、技能扫描等）；
9. 进入 CLI 运行路径，构造 `HermesCLI` 并执行一次性消息。

> 对 `hermes -z "hello"`，`--in` / `--resume` / `--continue` 都没有，第 4 步是空操作。

**这是本版最大的定位陷阱**：`HermesCLI` 不再是单文件类，而是 **17 个 Mixin 组装**：

主路径：

1. 加载 CLI 配置（`load_cli_config`）；
2. 初始化皮肤/显示；
3. 通过 `_init_agent()` 构造 `AIAgent`；
4. 对 `-z` 一次性消息，经 `CLIChatTurnMixin.chat()` 调用 Agent 的对话接口；
5. 将最终响应打印到终端。

### 5.5 Agent 门面：`agent/turn_facade.py` · `TurnFacadeMixin.run_conversation` `+0`

真实符号：

- 文件：`agent/turn_facade.py`
- 类：`class TurnFacadeMixin` `+0`
- 方法：`TurnFacadeMixin.run_conversation` `+0`
- 方法：`TurnFacadeMixin.chat` `+0`（`run_conversation(...)["final_response"]` 的薄包装）

**注意**：上一版文档把门面记作 `run_agent.py:AIAgent.run_conversation`。该符号**已不在
`run_agent.py` 中**——它随 god-file 拆分迁到了这里，`AIAgent` 通过 MRO 继承获得（详见
[04-核心模块与类型关系](./04-核心模块与类型关系.md)）。

该方法是**转发器 + turn 准入**，按源码顺序做：

1. `cancel_background_review_for_live_turn(self)`：后台 review 与本轮共享 `session_id`（为了缓存一致性），
   必须先取消或等它退出，再开启 live-turn 埋点；
2. 生成 `effective_task_id`（未传入时用 `uuid4()`）与 `relay_turn_id`
   （形如 `{session_id}:{task_id}:{8位hex}`），写入 `self._relay_pending_turn_id`；
3. 组装 `task_context = {session_id, task_id, platform}`；
4. `admit_durable_turn_lease(...)`（来自 `agent/turn_facade_lease.py`）：**申请跨进程持久化租约**。
   若返回 `early_result`（被取消/超时），经 `carry_unadmitted_user_message` 把用户消息带出去后**提前返回**；
5. 申请 relay 会话协调租约：`relay_runtime.SESSION_COORDINATOR.acquire_conversation(...)`；
6. `begin_turn(...)` 开启逻辑轮次，`start_task_run(...)` 开计量；
7. 设置三个 ContextVar 作用域：会话上下文、亲和作用域、计量上下文（`set_accounting_context`）；
8. 在 `bind_subagent_parent(self)` / `scoped_runtime_main({})` / `track_in_interrupt_scope(self)`
   三个上下文管理器内，`lease.start()` 后调用真实的
   `agent/conversation_loop.py` · `run_conversation` `+0`；
9. `finally` 中按固定顺序清理：`stop_refresher` → `join_threads` → `clear_interrupt` → `release`
   （顺序不可颠倒，见 [11-并发模型与生命周期](./11-并发模型与生命周期.md)）；
10. 返回结果 dict。

### 5.6 真实对话循环：`agent/conversation_loop.py` · `run_conversation` `+0`

真实符号：

- 文件：`agent/conversation_loop.py`（1745 行）
- 函数：`run_conversation` `+0`
- 作用：执行完整对话循环，直到模型不再返回 `tool_calls` 或达到预算/中断条件。

主路径：

1. 处理 MoA 消息解码；
2. 清理上一轮压缩状态；
3. 取消可能仍在运行的 background review；
4. 刷新 `.env` 凭据；
5. 调用 `agent/turn_context.py` · `build_turn_context` `+0` 做每轮 setup
   （它返回 `agent/turn_context.py` · `class TurnContext` `+0`）；
6. 组装 `messages` 和 `tool_schemas`（`build_api_messages` 在同一文件）；
7. 调用 LLM API；
8. 如果返回 `tool_calls`，逐个调用 `handle_function_call()`；
9. 将工具结果追加为 `tool` 消息；
10. 再次调用 LLM，直到得到最终文本；
11. 持久化消息并返回结果。

### 5.7 工具分发：`model_tools.py` · `handle_function_call` `+0`

真实符号：

- 文件：`model_tools.py`（987 行，**已从 1192+ 行版本拆薄**）
- 函数：`handle_function_call` `+0`
- 作用：把模型请求的工具名和参数分发到注册表。

主路径：

1. `coerce_tool_args(function_name, function_args)` 把字符串参数按 schema 转成正确类型
   —— **该函数已迁到 `tools/arg_coercion.py` · `coerce_tool_args` `+0`**，不再是 `model_tools.py` 的内部函数；
2. 处理 `tool_search` / `tool_describe` / `tool_call` 桥接工具；
3. 执行 pre-tool-call hook / middleware；
4. 在 `tools/registry.py` 的注册表中查找 handler；
5. 调用 handler；
6. 执行 post-tool-call hook；
7. 返回 JSON 字符串结果。

### 5.8 工具注册表：`tools/registry.py`

真实符号：

- 文件：`tools/registry.py`
- 常量：`_MAX_TOOL_ERROR_CHARS = 2048` `+0`（**该常量仍在原文件**，上一版的这条描述是对的）
- 函数：`discover_builtin_tools` `+0`
- 方法：`ToolRegistry.register` `+0`

主路径：

- 每个 `tools/*.py` 在 import 时调用 `registry.register()`；
- `register()` 保存 `ToolEntry`，包含 name、toolset、schema、handler、check_fn 等；
- `handle_function_call()` 通过注册表找到 handler 并执行。

> **易错点**：`check_fn` **不是**"进程级 TTL 缓存"。实测它是按 `(check_fn, scope)` 键的
> profile 维度缓存 + 30s TTL + 60s 失败宽限（抖动时沿用 last-good），另有
> `CHECK_FN_CACHE_BYPASS` 旁路。因此它依然**不能表达 per-session 状态**——会话级能力门控必须走
> toolset。详见 [06-工具系统与工具集](./06-工具系统与工具集.md)。

### 5.9 会话持久化：`hermes_state.py` · `class SessionDB` `+0`

真实符号：

- 文件：`hermes_state.py`（1697 行）
- 类：`class SessionDB` `+0`（**14 个 Mixin 组装**，与 `AIAgent` / `HermesCLI` 同一手法）
- 方法：`SessionDB.append_message` → `hermes_state_messages.py` · `SessionMessagesMixin.append_message` `+0`
- 方法：`SessionDB.get_messages` → `hermes_state_messages.py` · `get_messages` `+0`

**注意**：上一版文档把这两个方法记作 `hermes_state.py` 的内部方法。它们已随
god-file 拆分迁到 `hermes_state_messages.py`。

主路径：

- 会话开始时读取历史；
- 每轮结束后调用 `append_message()` 写入 user/assistant/tool 消息；
- 消息按 SQLite AUTOINCREMENT `id` 排序；
- 默认只读取 `active=1` 的消息（`get_messages` 的 `include_inactive` / `include_compacted`
  参数控制是否纳入被压缩/失效的行）。

> `append_message` 还带**门禁参数**（`compression_lock_holder` / `turn_lease_holder` /
> `turn_lease_ttl_seconds`）：它们不是表字段，而是写入前校验 `compression_locks` /
> `session_turn_leases` 表的租约凭据。详见 [08-数据模型与会话存储](./08-数据模型与会话存储.md)。

- LLM 返回 `tool_calls` 时如何分发；
- 消息最终如何写入 `SessionDB`；
- 响应如何回到终端；
- **改代码时去哪找方法体**：四大核心类（`AIAgent` 14 Mixin、`HermesCLI` 17 Mixin、`SessionDB` 14 Mixin、
  `GatewayRunner` 17 Mixin）都是 Mixin 组装，grep 不到方法就去对应的 `*Mixin` 文件。
