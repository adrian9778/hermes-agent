## 一、本层目标

第二层（02）已经用 `hermes -z "hello"` 把整条主路径走通。本层把这条链路**逐跳拆开**，讲清每一跳：

- 谁调用谁（调用方 → 被调用方）；
- 参数如何传递、如何消费；
- 返回值如何被处理；
- 状态如何变化；
- 错误如何传播（失败分支只标注去向，不铺开细节）。

本层仍以**主成功路径**为主。失败、重试、压缩、并发、插件钩子、缓存失效等复杂分支标注"第四层展开"，
不在这里铺开。每一跳都给出**调用关系表**（调用方与符号 | 关系 | 被调用方与符号 | 触发与输入 | 返回与后续处理 | 错误副作用）。

### 与上一版的差异（2026-11-16）

1. **主循环的角色关系已核实**：`agent/conversation_loop.py` · `run_conversation` `+0`（thin shell）
   与 `agent/turn_facade.py` · `TurnFacadeMixin.run_conversation` `+0`（turn 准入门面）**两个都存在但角色不同**：
   门面负责 turn 准入（租约、relay、作用域），薄壳负责"跑一轮 + 盖 turn 边界戳"。真实主循环在
   `agent/conversation_loop.py` · `_run_conversation_turn` `+0`。
2. **oneshot 主路径已改走网关**：`-z` 不再进 `cli.py` 的 REPL，而是 `_run_oneshot_from_args` →
   `launch_gateway_chat` → `run_gateway_chat` → 网关 RPC → `GatewayAgent`。
3. **`GatewayAgent` 不直接落库**：`GatewayAgent._persist_session` `+0` / `_ensure_db_session` `+0`
   是返回 `None` 的**桩**（占位替身），真正持久化经网关 RPC 在网关进程内完成。非网关路径才走
   `agent/session_persistence.py` · `SessionPersistenceMixin._persist_session` `+0`。
4. **`SessionDB` 已是 18 个 Mixin 组装**（02 写 16，实为 18，新增 `SessionPruneRewriteMixin` /
   `SessionApiContentMixin` / `SessionCoverageMixin`）。

### 跳 7：`agent/conversation_loop.py` · `run_conversation` `+0`（thin shell）与 `_run_conversation_turn` `+0`（实现）

#### 谁调用谁

- `TurnFacadeMixin.run_conversation` 调用 `agent.conversation_loop.run_conversation`；
- 薄壳把实际工作交给同文件的 `_run_conversation_turn`。

#### 参数

  persist_user_display_metadata=None, persist_user_platform_id=None, moa_config=None, turn_author=None,

#### 返回值

- `dict`，包含 `final_response`、`messages` 等；薄壳在返回前盖 `user_intervened`。

#### 状态变化

`run_conversation` 薄壳只做四件事（源码 docstring 明确）：

1. `agent._turn_user_intervened = False`；
2. 在 `native_turn_images(user_message)` 上下文内调用 `_run_conversation_turn(...)`
   ——本轮原生附带的图片在 turn 内对 `vision_analyze` 保持可见，避免同一批像素被二次嵌入同一请求；
3. `fence_result_reply(result)`、`lead_failed_turn_with_primary_auth`、`settle_held_final(agent, result)`；
4. `export_current_turn_boundary(agent, result, user_message)` `+0`
   （`agent/turn_context.py` · `export_current_turn_boundary`，378 行）：把 `{turn_id, current_turn_user_idx}`
   盖在**离开循环的每一个结果信封**上，且在**所有历史重写之后**（含 turn 后 micro-compaction）；
5. 写 `result["user_intervened"]`，`_close_durable_failed_turn(agent, result)`，返回。

`_run_conversation_turn`（1648 行，该文件 1973 行）的主路径：

1. 处理 MoA 消息解码；
2. 清理上一轮压缩状态；
3. 取消可能仍在运行的 background review；
4. 刷新 `.env` 凭据；
5. 调用跳 8 的 `build_turn_context()`；
6. 组装 `messages` / `api_messages` / `tool_schemas`（`build_api_messages` `+0`，`agent/turn_context.py` 1422 行）；
7. 调用 LLM API（跳 9）；
8. 若返回 `tool_calls` → 跳 10；
9. 追加 `tool` 消息后再次调用 LLM，直到得到最终文本；
10. 持久化（跳 11）并返回结果。

> 循环内每轮的实际工作被拆到 `agent/turn_*.py` 一族（`turn_preflight*`、`turn_api_call`、
> `turn_tool_round`、`turn_final_response` 等），见 `agent/AGENTS.md`。

#### 错误传播

- 循环内部有大量重试/恢复分支（`FailoverReason` 分类、凭据池轮换、fallback 链激活），
  见 [12-错误处理与重试机制](./12-错误处理与重试机制.md)；
- 主成功路径中，异常向上传播回 `TurnFacadeMixin.run_conversation`。

## 五、本层结论

读完本层，你应能：

- 按调用顺序复述主链路每一跳；
- 指出每跳的真实文件、函数/方法名，并知道**方法体可能不在同名的"大文件"里**；
- 区分 `TurnFacadeMixin.run_conversation`（turn 准入门面）与 `conversation_loop.run_conversation`（薄壳）
  与 `_run_conversation_turn`（真实主循环）三者的角色；
- 说明 `-z` oneshot 如何绕过 `cli.py` 走网关 RPC 路径，以及 `GatewayAgent` 的 `_persist_session`
  为何是返回 `None` 的桩（网关替身不直接落库）；
- 说明参数如何从 CLI 传到 Agent 循环（含 turn 准入阶段的租约与作用域）；
- 说明 LLM 返回工具调用时如何进入 `handle_function_call()`，以及 `coerce_tool_args` 已迁到 `tools/arg_coercion.py`；
- 说明最终消息如何通过 `SessionDB`（18 Mixin）与 `SessionMessagesMixin.append_message` 写入 SQLite；
- 知道哪些复杂分支留到第四层补齐。

**关键架构事实（2026-11-16）**：

1. **`-z` 绕过 `cli.py`**：`HermesCLI` 的 REPL 循环不启动，直接走网关 RPC 路径；
2. **网关代理是 `AIAgent` 的替身**：`hermes_cli/gateway_agent.py` · `GatewayAgent` 通过 RPC `prompt.submit`
   运行对话，不直接驱动本地循环；`_persist_session` / `_ensure_db_session` 是返回 `None` 的桩；
3. **会话创建在网关侧**：`session.create` RPC 调用在网关进程内创建/获取会话，然后绑定 `GatewayAgent`；
4. **持久化门面是 18 个 Mixin 组装**：`SessionDB`（`hermes_state.py` · `class SessionDB` `+0`），
   `append_message` 定义在 `hermes_state_messages.py` · `SessionMessagesMixin.append_message` `+0`。
